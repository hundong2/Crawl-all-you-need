# 멀티 LLM 기반 "사이트 -> 책" 생성 앱 목표 정의서 및 실행 계획

## 1) 문제 정의
- 목표: 특정 문서 사이트(예: `https://code.claude.com/docs/ko/overview`)를 전체 크롤링해 구조화된 Markdown(또는 PDF/EPUB/DOCX)로 변환하고, 책처럼 읽을 수 있는 결과물을 생성한다.
- 요구사항: UI에서 `회사 선택(Anthropic/OpenAI/Google)` + `모델 선택` + `사이트 URL 입력` + `출력 포맷 선택` 후 실행 가능해야 한다.
- 핵심 가치:
  - 문서 사이트 전체를 단일 지식 자산으로 보관
  - LLM 공급자 변경이 쉬운 추상화 계층
  - 재실행 시 증분 수집과 재생성(비용/시간 절감)

## 2) 기존 오픈소스 후보(재사용 우선)
아래 조합으로 대부분 구현 가능하며, "완전히 동일한 원클릭 앱"은 드물기 때문에 통합 개발이 현실적이다.

### A. 크롤링/콘텐츠 추출
- **Crawl4AI**
  - 장점: LLM 친화 추출 파이프라인, 동적 페이지 대응, 구조화 수집에 강함
  - 용도: 사이트 전체 페이지 수집 + 본문 정제
- **Scrapy + Playwright**
  - 장점: 대규모 크롤링 안정성, 커스텀 룰 제어, JS 렌더링 대응
  - 용도: 대량/복잡 사이트에서 정교한 크롤링 엔진
- **trafilatura / readability-lxml / boilerpy3**
  - 장점: 본문 추출 및 노이즈 제거
  - 용도: HTML -> 깨끗한 텍스트/마크다운 전처리

### B. 문서 변환/출판
- **Pandoc**
  - 장점: Markdown -> PDF/EPUB/DOCX 등 포맷 변환 표준
  - 용도: 최종 "책 포맷" 생성
- **mdBook (선택)**
  - 장점: 목차 기반 웹/문서형 결과물 구성 쉬움
  - 용도: HTML 기반 "책 형태" 프리뷰/배포

### C. LLM 다중 공급자 연동
- **LiteLLM**
  - 장점: OpenAI/Anthropic/Gemini 등 공급자 호출 인터페이스 통합
  - 용도: UI의 회사/모델 선택을 단일 API로 처리
- **LangChain (선택)**
  - 장점: 체인/분할/요약 파이프라인 구성 유연
  - 용도: 챕터 요약, 중복 제거, 톤 정리

## 3) 목표 범위(MVP)
- 입력:
  - 사이트 루트 URL 1개
  - 크롤링 깊이/도메인 제한 옵션
  - LLM 회사 + 모델 선택 콤보박스
  - 출력 포맷(MD/PDF/EPUB 중 1~N개)
- 처리:
  - 사이트맵/내부링크 기반 전체 수집
  - 페이지 정제 -> Markdown 변환
  - 문서 구조(챕터/섹션) 자동 재구성
  - LLM 기반 요약/중복 병합/스타일 통일(옵션)
- 출력:
  - `book.md` (필수)
  - `book.pdf`, `book.epub` (선택)
  - `manifest.json` (수집 URL, 실패 URL, 생성시간, 모델정보)

## 4) 비기능 요구사항
- 안정성: 실패 URL 재시도 및 실패 로그 저장
- 재현성: 동일 입력 시 동일 버전 결과물 추적(메타데이터 기록)
- 비용 통제: 토큰 사용량/예상 비용 표시
- 속도: 병렬 크롤링 + 캐시(변경 없는 페이지 재사용)
- 보안: API 키는 `.env` 관리, 로그에 키/민감정보 마스킹
- 법적/윤리: robots.txt, 이용약관 준수 및 사용자 책임 고지

## 5) 제안 아키텍처
- 프론트엔드:
  - `React + Vite` (회사/모델/URL/포맷 선택, 진행률 표시)
- 백엔드 API:
  - `FastAPI` 또는 `Node.js (Express/Fastify)`
  - 작업 큐(`Celery/RQ` 또는 `BullMQ`)로 장시간 크롤링 처리
- 크롤러 워커:
  - URL 큐 관리, 중복 제거, 본문 추출, markdown normalize
- LLM 서비스 계층:
  - LiteLLM adapter
  - provider/model별 파라미터 템플릿(temperature/max_tokens)
- 출판 파이프라인:
  - 챕터 조립 -> `book.md` 생성 -> Pandoc 변환
- 저장소:
  - 메타데이터(`SQLite/PostgreSQL`) + 아티팩트(`local/S3`)

## 6) 데이터 흐름
1. 사용자 입력 수신(회사, 모델, URL, 포맷)
2. 크롤링 계획 수립(도메인/깊이/중복 규칙)
3. 페이지 수집 및 본문 추출
4. Markdown 표준화 및 링크/이미지 정리
5. LLM 후처리(옵션: 요약/중복 제거/문체 통일)
6. 챕터 생성 및 목차 정렬
7. `book.md` 생성, 필요 시 PDF/EPUB 변환
8. 결과물 및 실행 리포트 반환

## 7) 구현 로드맵(6주 예시)
### 1주차: 기반 구성
- 리포 구조, `.env` 키 로딩, 기본 UI 폼
- LiteLLM 연동 및 공급자/모델 목록 관리

### 2주차: 크롤러 MVP
- 내부 링크 큐, 도메인 제한, depth 제한
- HTML 본문 추출 + markdown 변환

### 3주차: 책 조립
- 페이지 정렬 규칙, TOC 생성
- `book.md` 출력 + manifest 생성

### 4주차: LLM 후처리
- 챕터별 요약/중복 제거 옵션
- 비용/토큰 로그 및 실패 복구

### 5주차: 다중 포맷/UX
- Pandoc 변환(PDF/EPUB)
- 진행률 UI, 작업 히스토리, 다운로드

### 6주차: 품질/배포
- E2E 테스트, 성능 튜닝, 문서화
- Docker 기반 배포

## 8) 리스크 및 대응
- JS 렌더링 페이지 누락
  - 대응: Playwright fallback 렌더링
- 문서 구조 왜곡/중복
  - 대응: URL canonicalization + LLM dedupe
- 토큰 비용 급증
  - 대응: chunking, 캐시, LLM 후처리 옵션화
- 법적 이슈
  - 대응: robots/ToS 체크 안내 및 차단 옵션

## 9) 성공 지표(KPI)
- 수집 성공률 >= 95%
- 실패 URL 재시도 후 최종 성공률 >= 98%
- 100페이지 기준 처리시간 목표(예: 10~20분 이내)
- LLM 후처리 적용 시 사용자 만족도(가독성) 향상

## 10) 즉시 실행 가능한 작업 항목
1. 기술 스택 확정(FastAPI vs Node, Crawl4AI vs Scrapy)
2. MVP 범위 고정(MD만 우선, PDF/EPUB는 2차)
3. 샘플 사이트 2개로 POC 구현
4. 비용/속도 측정 후 모델 기본값 결정

## 11) MVP 완료 정의(Definition of Done)
- UI에서 회사/모델/URL/포맷 선택 후 실행 가능
- 사이트 전체 크롤링 결과를 단일 `book.md`로 생성
- 최소 1개 추가 포맷(PDF 또는 EPUB) 변환 성공
- 실패 로그/manifest/재시도 기능 동작
